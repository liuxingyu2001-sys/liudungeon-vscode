## 6.0 本章导航：文件清单、键名规则与容错

### 文件清单与「缺失会怎样」

```
plugins/liudungeon/
├── config.yml               插件主配置（6.1）
├── gui.yml                  GUI 菜单配置（见第五章）
├── data.db                  SQLite 数据库文件
├── maps/<模板名>/            地图模板（见第八章）
└── dungeons/<副本ID>/        一个副本 = 一个目录
    ├── config.yml           唯一必需的文件（6.2）
    ├── monsters.yml         怪物组（6.3）
    ├── stages.yml           阶段流程机（6.4）
    ├── zones.yml            区域与命名点位（6.5）
    ├── interacts.yml        交互点（6.6）
    ├── tasks.yml            定时/循环/事件任务（6.8）
    ├── rewards.yml          奖励（6.9）
    ├── chest_rewards.yml    箱子 UI 奖励（6.10）
    ├── scripts.yml          生命周期脚本钩子（6.11）
    └── *.js                 JavaScript 函数库（目录下所有 .js 都会被读入）
```

| 文件 | 必需 | 缺失的后果 |
|---|---|---|
| `dungeons/<id>/config.yml` | **是** | 该目录被**整份跳过**，报「缺少 config.yml」 |
| `monsters.yml` | 建议 | 记为问题，副本没有任何怪物可刷 |
| `scripts.yml` | 建议 | 记为问题，副本没有开场与结算流程 |
| `stages.yml` | 否 | 阶段机完全不介入，行为与没有阶段一样 |
| `zones.yml` | 否 | 没有区域与命名点位（引用点位处回退出生点） |
| `interacts.yml` / `tasks.yml` | 否 | 对应功能为空 |
| `rewards.yml` | 否 | `action.grant_reward` 会报「奖励不存在」 |
| `chest_rewards.yml` | 否 | 无箱子 UI（该文件当前整体未生效，见 6.12） |
| `*.js` | 否 | 脚本里不能调用自定义函数（`announceWave` 之类） |

目录级规则：

- **目录名就是副本 ID**，`/ld enter <ID>` 用的就是它（也支持用去色后的显示名）。
- 以 `.` 开头、或以 `_backup` 结尾的目录会被跳过（留给你放备份）。
- 示例目录 `dungeons/example/` 只在不存在时生成，**不会覆盖你改过的内容**。
- 示例的 `world.template` 是 `voidgen` —— 插件内置的虚空世界，所以**示例副本开箱即可进入**。

> **解析原则：任何一个文件写错，都不会让副本整体加载失败。**
> 问题会记进 `/ld doctor` 报告，其余部分照常工作。

### 中英双语键名

副本目录下的 10 个 YAML **都支持中文键名**（对齐 QueDP 的配置习惯）——
⚠ **唯一例外是 `scripts.yml`**：它的 7 个钩子名（`init` / `start` / `complete` / `exit` /
`fail` / `player_death` / `all_death`）**只认英文**，没有中文别名；
`start` 段内部的 `条件` / `脚本` 和连字符写法才有别名。
所以 `name` 与 `名称`、`location` 与 `位置` 都能用。

| 规则 | 行为 |
|---|---|
| 别名顺序 | 每个字段声明一串别名（英文主键 + 中文别名），**按声明顺序探测，命中即返回** |
| 优先级方向 | **各文件不一致**：`zones` / `stages` / `interacts` / `rewards 的保底段` 是**中文优先**；`monsters` / `tasks` / `chest_rewards` / 副本 `config.yml` 是**英文优先**。**同一字段不要中英都写**，否则结果取决于代码里的顺序 |
| 取不到值 | 一律**回落默认值**，不抛异常、不打断加载 |
| 主配置 | `plugins/liudungeon/config.yml` **不支持中文键**（走原版 `getConfig()`，键名写错 = 用默认值） |

### 类型容错规则（**「配了没反应」的第一嫌疑人**）

插件对写错的配置极其宽容：不崩、不报错、回落默认值。代价是**问题往往不显眼**。
下面这些写法都会**静默失效**：

| 字段类型 | 正确写法 | ⚠️ 会静默失效的写法 |
|---|---|---|
| 整数 | `1800`、`"1800"` | `1800.0`（小数回落默认值，**不是**取整）、留空 |
| 布尔 | `true` / `false`；字符串 `"true"/"1"/"yes"/"on"/"是"/"开"` 与 `"false"/"0"/"no"/"off"/"否"/"关"` | **写成数字 `1` / `0`（不带引号）** —— YAML 解析成整数后，`isBoolean` 与 `isString` 都为 false，于是**回落默认值**。这是最容易踩的一条 |
| 字符串列表 | YAML 列表；单个字符串（当作一项）；多行块 `\|-`（整块当作**一条**脚本，可含 if/else）| `''` 空串 → 空列表（等价于没写） |
| 子段 | `xxx:` 缩进若干行；`xxx: {}` 也可 | 只写段名不给内容（值为 null）等价于「没写这一段」 |
| 含特殊字符的值 | 加引号，如 `范围: '0,64,0 ~ 10,70,10'` | 冒号后漏空格（`范围:'a~b'`）会被当成一个普通键名 |
| 列表形态的键名 | `monsters` / `items` / `options` | **列表形态只认英文键名**。写成 `怪物:` + 列表不会生效，该组会变成 0 个怪物并直接判定完成 |

> **排查口诀：「配了没反应」先看类型。** 绝大多数是布尔写成了 `1`、整数写成了 `1800.0`，
> 或者把段写成了标量。

> **脚本字段统一写成 `|-` 块**：一行一条语句、行尾加分号，例如
> `complete: |-` 下面依次写 `action.title(...);` / `action.grant_reward(...);`。
> 块里是纯 JavaScript，注释要用 `//`（写 YAML 的 `#` 会变成语法错误）；
> 也别给整行套引号 —— 那会变成一个什么都不做的字符串字面量。
> 老配置里的 `- "action.xxx()"` 列表写法仍然兼容。完整规则见
> [07 的 7.1.1](07-脚本开发指南.md#711-脚本怎么写统一这一种排版)。

开启后会在启动后自动跑一次核心链路自检（模板克隆 → 世界加载 → 世界规则 →
脚本执行 → 刷怪 → 击杀推进 → 世界销毁），结果打到控制台。**生产环境保持关闭。**

### 出本时到底还原了什么

插件会在进本时记录一份玩家状态快照，出本时用来恢复。**分三类，行为固定，没有开关：**

| 类别 | 内容 | 出本时 |
|---|---|---|
| **还原** | 位置（回进本前站的那一点）、游戏模式与飞行（倒下等复活时被切成旁观者，不还原会卡住） | **一律还原** |
| **出本兜底**（不是还原旧状态，是避免带伤出门） | 副本结束时仍处于**倒下 / 已阵亡**状态的玩家 | 扶起来：切回生存、给**半血**、灭火、60 tick 无敌（不扣复活次数、不发消息、不跑复活脚本） |
| **不还原**（2026-09-16 起停用） | 血量、饱食度、着火、空气、**药水效果**、移速与飞度、发光 | **一律不动** —— 副本里的变化会带回主世界，需要的话自己用脚本收尾 |
| **产出类**（副本里的变化属于成果） | **背包**（物品+盔甲+副手）、**经验** | **一律不碰** |

> **⚠ 为什么把「状态类」停用了**：原来的实现里，采集血量上限时取的是
> `attr.getValue()`（**基数 + 装备/其他插件给的修饰符**），还原时写的是
> `attr.setBaseValue(...)`（**基数**）。两者不对称，于是玩家只要穿着一件加血量上限的
> 装备（或装了别的加血插件），**每进/出一次副本，基数就被抬高一次修饰符的量**：
> `20(+10) → 30(+10) → 40(+10) → …`，血量上限越刷越高、且不会自己降回来。
> 现在这一节整体停用；代码保留在 `PlayerSnapshot.restore()` 里备用，重新启用前
> 必须先确认采集侧读的是 `getBaseValue()`（已改）并按还原后的实时上限夹取血量。
>
> 停用后的副作用，出本前请自行留意：**药水效果不会清**（副本 buff / 诅咒会跟出本）、
> **血量/饱食度/着火状态保持副本里的样子**、**被脚本改过的移速不会自动恢复**。
> 唯一的例外是「倒下 / 已阵亡」的玩家：他们进副本时被压到 1 点血，所以出本会被
> 扶起来给半血（见上表第二行），否则等于带着 1 点血站在主世界等死。
>
> **为什么产出类不还原**：快照记的是你**进本前的装备**，而插件从不在进本时
> 清空或替换背包。所以覆盖回去只会抹掉你在副本里拿到的东西 ——
> 包括 `action.grant_reward()` 发的奖励、捡到的战利品、`action.give_exp()` 的经验。
>
> 通关脚本的典型写法是「先 `grant_reward` 再 `exit_dungeon()`」，
> 还原背包会让**奖励在发出的同一秒被抹掉**。
>
> 这里**故意不提供开关** —— 能配错的东西迟早会被配错。

## 6.2 副本 `config.yml`

### 顶层 `enable` / `hide` —— 副本总开关与隐藏

| 键 | 默认 | 作用 |
|---|---|---|
| `enable` | `true` | `false` = **停用**：GUI 里显示为屏障、任何进入途径都被拒 |
| `hide` | `false` | `true` = **不在列表里显示**（GUI 与 `/ld list` 都看不到），但 `/ld enter <副本ID>` 仍可进入 |

两个键都可以写中文（`启用` / `隐藏`），也接受 `enabled` / `hidden`。

```yaml
enable: true      # 能不能进
hide: false       # 列不列出来
```

**两者的分工**：

| 想要的效果 | 怎么配 |
|---|---|
| 这个副本临时下线，谁都别进 | `enable: false` |
| 副本能玩，但不想挂在列表里（活动副本 / 测试副本 / 只给特定队伍） | `hide: true` |
| 完全删掉 | 删目录（会连带丢掉配置与地图关联，不推荐） |

`hide: true` 不影响进入条件 —— 知道 ID 的人照样能进；要限制人请用 `requirements`
的权限 / 等级 / 门票，或干脆 `enable: false`。
带 `liudungeon.admin` 权限的玩家**始终能看到**隐藏的副本（方便自己调试）。

### 顶层 `enable` 详解 —— 停用之后会发生什么

`enable: false` 时：

- GUI 列表里显示为**屏障**（不可点击，注明「该副本已停用」）；
- 任何进入途径（GUI / `/ld enter` / 脚本 `action.*`）都被拒，提示「该副本当前已停用」；
- **配置照常加载** —— `/ld doctor` 依然能体检它，改回 `true` 再 `/ld reload` 即可上线。

停用的判断排在进入校验的**最前面**：不会因为「人数不足」「冷却中」给出误导性的拒绝原因。

**为什么停用还要加载配置**：临时下线一个副本时，删目录会连带丢掉配置与地图关联；
`enable: false` 只是关掉入口，改回 `true`（或去掉这行）再 `/ld reload` 即可上线。

> 与 `requirements` 段的区别：`requirements` 是**对玩家**的限制（等级/人数/费用），
> `enable` 是**对整个副本**的开关 —— 它连"求"的机会都不给，校验顺序上排在最前面。

> ⚠️ **不要改内置示例里的这两个默认值**：`src/main/resources/example/config.yml`
> 同时是 `/ld create <副本ID>` 抄给新副本的**母本**（原样复制，只改写展示名与模板名）。
> 把它改成 `enable: false` 的话，以后每个新建副本一出生就是停用且不在菜单里显示的。
> 要下线某个副本，改**那个副本自己**的 `config.yml`
> （见 [第三十八节](../04-开发进展记录/10-建本母本与扩展打包.md)）。

#### 演示副本 `example` 不在这两个键的管辖范围内

首次启动时插件会写出 `dungeons/example/`（内置示例）。它是**插件自己的演示数据**，
不是你建的副本，所以：

- **不出现在 GUI 菜单、`/ld list`、任何指令补全里**，连管理员也不显示
  —— 与 `hide: true` 不同，那是个"配置状态"，而演示副本是插件的固定行为；
- 但**照常可用**：`/ld enter example`、`/ld info example`、`/ld edit enter example` 都能进；
- 照常参与 `/ld doctor` 体检、照常出现在「模板被谁引用」里 —— 这些是诊断信息，藏起来反而查不到问题。

想让某个副本"谁都不列"是做不到的（`hide: true` 对管理员仍可见）；
想拿演示副本当起点，用 `/ld create <副本ID>` 建一份自己的，别直接改它。

### `dungeon` 段 —— 基础信息

| 键 | 默认值 | 说明 |
|---|---|---|
| `name` | 副本 ID | 显示名，支持颜色代码 |
| `icon` | `DIAMOND_SWORD` | GUI 里的图标材质 |
| `difficulty` | `普通` | 难度标签，仅展示 |
| `description` | 空 | 描述行列表 |
| `death_check_mode` | `strict` | `strict` / `lenient`。⚠️ **仅用于 `/ld info` 展示，不影响实际行为** —— 全灭判定固定走"还有人能起来就不算全灭"的逻辑。见 [6.11](#611-已解析但未生效的字段) |

### `world` 段 —— 世界配置

| 键 | 默认值 | 说明 |
|---|---|---|
| `template` | `voidgen` | 模板名，对应 `plugins/liudungeon/maps/<这个名字>/`。**默认的 `voidgen` 是插件内置的虚空世界**（首次启动自动生成，只有几百字节、无区块文件，地板是 y=64 的一层基岩）—— 所以不导入任何地图也能开本。换成自己的地图：`/ld template import <地图名> [模板名]`，再把这里的名字改掉 |
| `spawn` | `0,64,0,0,0` | 出生点 `x,y,z,yaw,pitch`（写在 **`world` 段**里）。**不需要精确**，插件会自动找安全落脚点。⚠ 写在 `dungeon` 段里的 `dungeon.spawn` **不生效**（没有任何读取点，`/ld doctor` 会报出来）—— 出生点只有这一处 |
| `border` | `-1` | 世界边界**半径**，`-1` = 不设置。见下方注意 |
| `world_rules` | 内置默认 | 见下 |

`world_rules` 内置默认值（共 **10 条**，逐条取自 `WorldRuleApplier.recommendedDefaults()`，
用 Paper 26.x 的**新式 id**，不是旧教程里的驼峰名）：

| 规则 | 值 | 作用 |
|---|---|---|
| `keep_inventory` | `true` | 死亡不掉落（副本必开） |
| `spawn_mobs` | `false` | 关自然刷怪，由怪物组精确控制 |
| `advance_time` | `false` | 关昼夜交替 |
| `advance_weather` | `false` | 关天气循环 |
| `mob_griefing` | `false` | 关怪物破坏方块 |
| `natural_health_regeneration` | `false` | 关自然回血 |
| `show_advancement_messages` | `false` | 关成就播报 |
| `immediate_respawn` | `false` | 保留死亡界面（复活系统需要） |
| `mob_drops` | `true` | 怪物掉落 |
| `entity_drops` | `true` | 实体掉落 |

> ⚠ **不要照抄旧教程里的 `doFireTick` / `doMobSpawning` 这类驼峰名**：
> 26.x 已把 GameRule 改名，`doFireTick` **被移除且没有等价项**（插件刻意不做映射，
> 让它报成"未知规则"而不是静默映射到别的规则）。旧名里除 `doFireTick` 外其余都有映射，
> 但建议直接写新名。

```yaml
world_rules:
  time: night                # 时间：day / night / 数字 tick；⚠ 不写时默认【不改世界时间】
  storm: false               # 是否雷雨
  keep_inventory: true
  spawn_mobs: false
  advance_time: false
  natural_health_regeneration: false
  mob_griefing: false
```

> **Paper 26.x 的 GameRule 名称改成了「下划线小写」**（`keep_inventory`、`spawn_mobs`、
> `advance_time`…），旧的驼峰写法（`keepInventory`、`doDaylightCycle`）插件做了兼容映射，
> 但建议直接用新名字。名字写错时**不会报错，只是那条规则不生效** ——
> 这是最容易漏的坑，改完记得进本实测。
>
> **边界有两个键，别搞混**：`world.border` 和 `world.world_rules.border` 都能用，
> 优先级是 `world_rules.border` > `world.border`。只写一个即可。
> （早期版本里 `world.border` 是个**从未被读取的死字段**，照着示例配了等于没配；
> 现已修复为回退值，两个键都真正生效。）

**GameRule 的容错细节**（`world_rules` 段里除 `time` / `storm` / `border` 三个保留键外，
**其余所有键都会被当成 GameRule 写入**）：

`GameRule.getByName` 是**精确大小写查表**，写错会静默返回 null。插件为此在 `WorldRuleApplier.lookup()` 里做了多级容错：

```
原样查  →  补 minecraft: 前缀  →  驼峰转下划线再补前缀  →  去命名空间/下划线后全量归一化匹配
```

所以 `keep_inventory`、`keepInventory`、`KEEP_INVENTORY`、`minecraft:keep_inventory`
**都能命中**。旧教程的名字另有映射表：

| 旧名 | 26.x 新名 |
|---|---|
| `doDaylightCycle` | `minecraft:advance_time` |
| `doWeatherCycle` | `minecraft:advance_weather` |
| `doMobSpawning` | `minecraft:spawn_mobs` |
| `naturalRegeneration` | `minecraft:natural_health_regeneration` |
| `announceAdvancements` | `minecraft:show_advancement_messages` |

`doFireTick` 在 26.x **已被移除且无等价项** —— 它会被报成「未知规则」而不是静默映射到别处，
这是刻意的（比悄悄改成别的行为诚实）。

每条的生效结果会打印在日志与 `/ld doctor` 里：「已应用 N 条，未知规则 N 条，失败 N 条」，
**改完 GameRule 一定要看这行**。

值类型不统一（`random_tick_speed` 是整数，其余多为布尔），由代码按 `GameRule.getType()` 分派，
类型不支持的值会被记入「失败」列表而不是崩服。

### `revive` 段 —— 复活系统

**有键才启用**：写了 `auto.delay` 就是要自动复活，没写就是不要。
（不存在 `enabled: true` 这种写法。）

| 键 | 默认值 | 说明 |
|---|---|---|
| `count` | `0` | 复活次数，`-1` = 无限，`0` = 禁止。⚠ 默认 **`0`（禁止复活）** —— 想要复活必须显式给次数 |
| `count_mode` | `shared` | `shared` 全队共用一个池 / `independent` 每人各自计数 |
| `auto.delay` | 未启用 | 自动复活延迟（秒） |
| `auto.at` | `spawn` | 落点：`spawn` 出生点 / `inplace` 原地 / `区域.点位` |
| `ally.cast_time` | 未启用 | 队友读条秒数 |
| `ally.range` | `4.0` | 队友救援距离 |
| `ally.consume_count` | `true` | 队友救起是否消耗次数 |
| `ally.at` | `inplace` | 落点 |
| `on_revive` | 空 | 复活成功后执行的脚本，`@trigger` = 被复活者 |
| `on_exhausted` | 空 | 复活成功且**剩余次数刚变为 0** 时执行一次（人已经站起来了，副本继续 —— 这不是"结束"） |

三种方式**可以同时开启，谁先成立谁生效**。注意 `auto.at: spawn` 会把人送回出生点，
而 `ally.at: inplace` 是在原地救起 —— 想让队友救援更有价值，可以考虑把自动延迟调大。

⚠ **`count` 与三种方式是「与」的关系**：`count: 0`（含不写）等于禁止复活，
此时 `auto` / `item` / `ally` 配了也不会生效 —— 玩家倒下会被切成旁观者，却没有任何办法起来，
`/ld doctor` 会报出来。想要复活就必须给次数（正数，或 `-1` 无限）。

⚠ **次数池是唯一的"资源"**：自动复活、道具复活、队友救起（`consume_count: true` 时）
都从同一个池里扣。池子空了之后剩下的人只能靠 `count: -1` 或脚本 `action.revive()` 起来。

#### 次数为 0 时不会再提示"还有救"

倒下提示只列**真能成功**的路。只要是"扣次数"的方式，次数为 0 时一律不提示、不挂号：

| 次数为 0（池子被用光）时 | 行为 |
|---|---|
| 自动复活 | **不挂倒计时** —— 不再发「N 秒后自动复活」，动作栏也不再有「自动复活倒计时 N 秒」 |
| 道具复活（`consume_count: true`） | **不显示**「点击使用 xx 复活」按钮（否则道具会被扣掉、人却没起来） |
| 队友救起（`consume_count: true`） | 队友读条到点会被拒绝（「该玩家已没有复活次数」），不算"有人能来救" |
| 道具 / 队友救起（`consume_count: false`） | 照常提示、照常能救 —— 次数为 0 也成立 |
| 都不成立 | 只发一句「&c复活次数已用完&7 —— 没有可用的复活方式了」，紧接着按"确认阵亡"处理 |

判定"这个人还有没有机会"用的是**同一套规则**（`ReviveService.planDowned()`，纯函数），
所以不会出现「提示说 5 秒后自动复活、系统却同时判他阵亡」这种自相矛盾。
规则清单可以直接跑：`bash tools/verify-revive-prompt.sh`。

#### 次数耗尽 / 全队阵亡之后会发生什么

这两件事**不是一回事**，配置时容易混：

| 事件 | 触发时机 | 副本会怎样 |
|---|---|---|
| `on_exhausted` | 某次复活**成功**、剩余次数刚变成 0 | **继续**：人被救起来了，只是再倒下就没有机会了。适合发提示 |
| `all_death` | 全队都处于「已阵亡」、没人能再起来 | 先跑 `scripts.yml` 的 `all_death` 脚本；**脚本跑完后若仍然没有一个活人，插件自动判失败并在 10 秒后把所有人传回主世界** |

`all_death` 里想自定义收尾就自己写：

```yaml
# scripts.yml
all_death: |-
  action.title('@all', '&c&l全队阵亡', '&7副本失败，正在退出…');
  action.fail('全队阵亡');   // 判失败：跑 fail 钩子 → 10 秒后全员退出
  // action.revive('@all');   // 或者给一次"复活赛"，那就不会判失败
```

> 内置示例的 `scripts.yml` 就是这么写的（可以直接照抄）。
> 早于本版的插件在这里只有"执行脚本"这一步：不写 `all_death` 的队伍**会被一直留在副本里**
> （旁观者视角、既起不来也出不去，实例还占着世界与槽位）。

**日志级别说明**：次数用光后自动复活失败，日志是 **`INFO`** 级别
（`[复活] 玩家 自动复活失败：复活次数已耗尽 —— revive.count: 1，全队共用一个池，剩余 0；这不是报错…`）
—— 这是配置按预期生效的结果，不是故障；真正的黄字 `WARN` 只留给一种情况：
`revive.count: 0`（禁止复活）却还留着 `auto` 倒计时，那种配置自相矛盾、倒计时永远不可能成功。

> 本版起这条日志很少再出现：倒下那一刻次数就已经是 0 的，根本不挂自动倒计时（见上一节）。
> 现在只有一种情形还会走到它 —— `count_mode: shared` 的队伍里，某个人的倒计时**正在走**，
> 最后一次机会被队友用掉了，他到点时自动复活才会失败。这时该玩家会被判"确认阵亡"。

## 6.3 `monsters.yml` 怪物组（波次）

```yaml
groups:
  wave_1:
    spawn_timing:
      type: AUTO_START      # 见下表
      delay: 0              # DELAYED 时的延迟秒数
    condition: []           # 可选：条件成立才刷
    on_start: |-            # 刷怪前执行
      announceWave(1, '第一波', '清理所有敌人');
    on_end: |-              # 该组清空后执行
      action.message('@all', '&a第一波已清除！');
      action.wait('3秒');
      action.spawn_group('wave_2');
    monsters:
      - id: Zombie
        location: '0,64,-10'
        amount: 3
        level: 1
```

**`spawn_timing.type` 取值**

| 值 | 含义 |
|---|---|
| `AUTO_START` | 地牢开始时自动刷新 |
| `DELAYED` | 地牢开始后延迟 N 秒刷新 |
| `TRIGGERED` | 指定怪物组完成后自动触发（配合 `trigger_group`，**与 `spawn_timing` 同级**） |
| `MANUAL` | 手动用 `action.spawn_group()` 触发 |
| `SCRIPTED` | 由脚本控制 |

**推荐写法（不用写脚本）：第一波 `AUTO_START`，后续波次 `TRIGGERED`。**

```yaml
groups:
  wave_1:
    spawn_timing:
      type: AUTO_START        # 进本立刻刷
    monsters:
      - { id: Zombie, location: '0,64,-10', amount: 3 }

  boss:
    spawn_timing:
      type: TRIGGERED
    trigger_group: wave_1     # ⚠ 写在组这一层，不要写进 spawn_timing 里面
    on_end: |-
      // Boss 清空 = 通关
      action.complete_dungeon();
    monsters:
      - { id: Husk, location: '0,64,-20', amount: 1, boss: true }
```

> `trigger_group` 的位置很容易写错：它读的是**组这一层**的键。
> 写进 `spawn_timing:` 里面不会报错，但那一组永远不会被触发 —— 玩家打完第一波后
> 就卡住了，而且没有任何提示，是新手最常见的一个坑。

> 想精确控制节奏（例如"等玩家踩了踏板再放下一波"）时，再用
> **`MANUAL` + 上一波的 `on_end` 调 `action.spawn_group('下一波')`**。

**怪物 `id` 的解析规则**（按顺序尝试）

1. 装了 MythicMobs 时，**优先当成 MM 怪物 ID**（如 `DZ_僵尸`、`Elite_Guard`）
2. 否则按原版实体名解析，大小写不敏感，也支持 `DZ_ZOMBIE` 这类带前缀的写法
   （依次尝试整名、大写、最后一段下划线之后、第一段下划线之前）

**组级增强字段（全部可选）**

| 字段 | 说明 |
|---|---|
| `zone` | 组默认区域，成员可用 `point` 引用该区域的点位 |
| `repeat.interval` | 重复生成间隔（tick） |
| `repeat.max` | 重复次数上限（**必须有**，否则无限增援） |
| `repeat.wait_cleared` | 前一轮没清完就跳过本轮（不计入轮次） |

**成员级增强字段（全部可选）**

| 字段 | 说明 |
|---|---|
| `point` | 引用 `区域.点位`；写 `区域.点位` 可跨区域 |
| `amount: "3-6"` | 区间随机，单成员单次上限 32 |
| `chance: 30` | 30% 概率出现 |
| `delay: 60` | 延迟 60 tick 生成 |
| `boss: true` | 击杀触发 `boss_kill` 任务并推进阶段 |
| `when: "getVar('难度') >= 3"` | JS 表达式，不成立则跳过 |
| `replace_with: Elite_Guard` | `when` 成立时改用这个 ID |

## 6.4 `stages.yml` 阶段流程机

给副本一条主线「清怪 → 开门 → Boss → 结算」，**完全事件驱动，没有定时器轮询**。
不建这个文件 = 副本行为与以前完全一致。

```yaml
入口: 清怪

清怪:
  名称: '&e清理前厅'
  通关条件: "dungeon.isGroupCleared('wave_1')"   # JS 表达式，返回真值即完成
  超时: 300                                       # 秒，0 或不写 = 不限时
  开始脚本: |-
    action.title('@all', '&e第一阶段', '&7清理所有敌人');
    action.spawn_group('wave_1');
  通关脚本: |-
    action.setblock('20,64,0,AIR');
  超时脚本: |-
    action.fail('前厅超时');
  下一阶段: Boss战

Boss战:
  通关条件: "dungeon.isGroupCleared('wave_2')"
  下一阶段:                       # 分支写法：按列表顺序判定，第一个成立的命中
    - 目标: 隐藏房
      条件: "getVar('找到密道') == 1"
    - 目标: 结算                   # 无条件兜底
```

字段：`名称`、`通关条件`、`超时`、`开始脚本`、`通关脚本`、`超时脚本`、`下一阶段`。

- `下一阶段` 写单个名字 = 无条件跳转
- 写列表 = 按顺序判定分支，**都不成立则走无条件兜底**
- 没有兜底则视为最终阶段，副本直接通关
- 跳转最多 8 跳，防止配置写出死循环

## 6.5 `zones.yml` 区域与命名点位

**最大价值：坐标只写一次**，怪物组 / 交互点 / 传送脚本都引用同一份，改图时只改这个文件。

单副本最多 **64 个区域**，只支持长方体（AABB），不支持球形/多边形。

```yaml
战斗区:
  名称: '&e前厅战斗区'
  范围: '-20,60,-30 ~ 20,80,10'   # 两点顺序随意
  默认开启: true
  进入脚本: |-
    action.message('@trigger', '&e你进入了前厅战斗区');
  离开脚本: |-
    action.message('@trigger', '&7你离开了前厅战斗区');
  点位:
    中心: '0,64,-10'
    落点: '0,64,0,0,0'            # 带朝向的点位用于传送
```

`默认开启: false` 的区域开局不生效，由脚本 `action.enable_zone('区域名')` 打开。

## 6.7 `tasks.yml` 任务

```yaml
tasks:
  # 定时任务：在副本运行到指定秒数时执行
  countdown:
    type: 定时                        # 也接受 schedule
    times:
      300: |-
        action.message('@all', '&e还剩 5 分钟！');
      60: |-
        action.sound('@all', 'ENTITY_ENDER_DRAGON_GROWL');

  # 循环任务：每隔固定秒数执行
  buff_timer:
    type: loop
    interval: 60
    script: |-
      action.apply_potion('@all', 'SPEED', '10s', 0);

  # 事件任务
  wave_complete_task:
    type: event
    trigger: wave_complete
    trigger_target: wave_1
    script: |-
      action.message('@all', '&a第一波已完成（事件任务）');
```

## 6.8 `rewards.yml` 奖励

```yaml
rewards:
  # ---------- 固定奖励 ----------
  通关奖励:
    items:
      - type: item          # item = 原版物品；mythic_item = MythicMobs 物品
        id: DIAMOND
        amount: 5
    money: 1000
    exp: 500
    commands:
      - "give %player% golden_apple 3"

  # ---------- 随机奖励（权重轮盘 + 保底）----------
  随机宝箱:
    type: random
    保底:
      次数: 30              # 抽 30 次没出「传说」，第 30 次必出
      必出: 传说
      软保底起始: 10        # 从第 10 次开始给目标项提权，0 = 不启用
      软保底增幅: 2.0       # 每次未出，目标项权重 ×该值
      计数域: 副本          # 副本 = 按 副本ID:奖励名 计数；全局 = 跨副本共用
    options:
      普通: { weight: 70, items: [{ type: item, id: IRON_INGOT, amount: 10 }] }
      稀有: { weight: 25, items: [{ type: item, id: DIAMOND, amount: 3 }] }
      传说: { weight: 5,  items: [{ type: mythic_item, id: epic_weapon, amount: 1 }], money: 5000 }
```

保底计数**跨场次持久化**（存在数据库里），所以玩家反复刷同一个副本时保底是累计的。

## 6.12 改完配置怎么生效

| 改了什么 | 怎么生效 |
|---|---|
| 插件 `config.yml` | `/ld reload` |
| 副本配置（`dungeons/<id>/*.yml`） | `/ld reload` |
| 副本配置，但用**游戏内编辑模式**改的 | `/ld edit save` 或 `/ld edit test` —— **写盘后会自动全量重新解析，等于替你敲了一次 `/ld reload`**，不用再手动 reload |
| `gui.yml` | `/ld menu reload`（或 `/ld reload`） |
| 地图模板 | `/ld template reload` |
| 地图**地形**（挖/放的方块） | 编辑会话里 `/ld edit save` 会异步同步回模板，`/ld edit test` 是同步等待；用 `/ld template import` 导入的走导入流程 |
| **已经开着的副本实例** | **不受影响**，新配置对下一次开本生效 |

改完建议跑一次 `/ld doctor`，它会校验配置、脚本条件表达式与模板是否就绪。
